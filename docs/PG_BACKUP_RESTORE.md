# PostgreSQL backup and restore rehearsal

The `postgres-rls.yml` GitHub Actions workflow now tests a **disposable CI-only PostgreSQL 16 backup/restore** using `pg_dump -Fc -n ms` and `pg_restore` into a separate newly created database. It checks row counts for organizations, merchants, candidates, evidence, recommendations and audit events, and compares every `ms` table's row count and canonical JSONB row-content digest, plus each schema sequence's `last_value` and `is_called` state (including the empty-inventory case), along with schema, relation/sequence and routine ACL parity, plus restored column metadata (including defaults, identity and generated expressions), constraints, index definitions, user-defined trigger definitions, SQL function/procedure signatures and bodies (including execution-security flags), RLS flags and policy definitions. This catches changed rows even when counts match, and detects missing or altered schema objects after restoration, including audit triggers, security-definer functions or default expressions that row-count checks cannot detect. The digest is an integrity regression check, not a cryptographic proof of a trustworthy backup or a substitute for restore drills.

## Authentication ACL regression gate
The restore deliberately retains schema object ACLs (no `--no-acl` flag). The CI test checks both source and restored databases: neither `ms.login_account` nor `ms.lookup_session` may grant `EXECUTE` to `PUBLIC`, while the narrowly scoped `merchant_auth` role must retain `EXECUTE` on both. An additional effective-privilege check asserts that `merchant_runtime` cannot execute either function in the source or restored database, including via inherited grants. This checks an actual role's effective permissions rather than incorrectly treating PostgreSQL's `PUBLIC` pseudo-role as a login role. This guards against the PostgreSQL default `PUBLIC EXECUTE` privilege on newly created functions, especially dangerous for `SECURITY DEFINER` authentication lookups. The disposable restore shares cluster-global roles with the source; this is not a fresh-cluster disaster recovery test.

## Scope limitations
- This is an automated CI rehearsal, **not** evidence that a production backup schedule, offsite encryption, immutable retention, PITR/WAL archive, replica failover or disaster recovery configuration exists.
- The archive is kept on the temporary GitHub runner and not uploaded as an artifact, so synthetic identities and data are not persisted externally.
- Never run a restore into a working production database or with production secrets without a separately approved change and tested rollback plan.
- PostgreSQL roles are cluster-global and are not included in a schema-only `pg_dump`: for recovery onto a new server, provision the minimum necessary roles first via audited migrations, or use a reviewed `pg_dumpall --globals-only` and protect it as a privileged secret.
- Schedule encrypted production backups, test restore to an isolated host, compare row counts and policy enforcement, and document RPO/RTO before launch.

## Release gate
- CI must pass all backup/restore checks on the exact release commit. The metadata comparisons cover the `ms` schema; they do not prove recovery of cluster-level roles, grants, extensions, or production scheduling.
- Production acceptance additionally requires an **actual encrypted, access-controlled backup** and observed restoration time into a separate environment, both approved by operations/security.

## SECURITY DEFINER grant hardening (2026-11-20)
The exact-head PostgreSQL CI run [44644232864](https://github.com/overurdream-collab/Merchant-scope/actions/runs/44644232864) failed the new catalog-wide guard: 18 tests passed and two negative privilege checks failed. PostgreSQL default EXECUTE grants exposed six SECURITY DEFINER functions to PUBLIC and merchant_runtime: audit_change, guard_lead, guard_recommendation, guard_research_candidate, has_role, and is_member. Migration `004_definer_permissions.sql` revokes direct execution of all SECURITY DEFINER routines from PUBLIC and merchant_runtime, then explicitly grants only the two RLS membership predicates to merchant_runtime. The authentication routines remain merchant_auth-only; trigger routines remain invoked by triggers, not directly by the runtime. The disposable test fixture applies migration 004 before the catalog-wide negative checks. For any existing environment, migration 004 must be applied with an authorized schema owner before acceptance; it is not automatically applied to live databases. Re-run CI on the final commit and confirm the browser, backup/restore, and ACL checks; the fix is not considered validated until those checks succeed.

## Exact runtime predicate allowlist regression (2026-11-20)
The [PostgreSQL CI run 44651974010](https://github.com/overurdream-collab/Merchant-scope/actions/runs/44651974010) on `7020a509` reported **19 passed, 1 failed**: migration 004 correctly left `ms.has_role(ms.member_role)` and `ms.is_member()` executable by `merchant_runtime` for RLS, but the new catalog-wide test incorrectly expected zero executable SECURITY DEFINER routines for that role. Commit `bd70cb4` corrects the assertion to an **exact** allowlist: `PUBLIC` must execute none; `merchant_runtime` must execute precisely those two predicates and no other SECURITY DEFINER function. Both unexpected exposure and missing required predicate grants fail the test. This change is a test correction, **not** evidence that the full PostgreSQL/browser/restore workflow passed; verify the workflow on the new exact head before closing the gate.

## View-definition restore regression (2026-11-20)
The CI restore rehearsal now compares the complete inventory and `pg_get_viewdef` SQL definitions of ordinary (`v`) and materialized (`m`) views in schema `ms` between the disposable source and restored databases. This closes a metadata blind spot: equal base-table row digests and RLS policies do not establish that views survived restoration unchanged. The comparison handles an empty inventory. Evidence is the PostgreSQL RLS workflow on the exact commit containing this check; passing earlier runs does not validate this addition. It remains a same-cluster synthetic rehearsal, not production disaster recovery.

## Effective schema ACL parity regression (2026-11-20)
The restore workflow previously compared `pg_namespace.nspacl::text` literally even though a NULL ACL represents PostgreSQL owner-default privileges and an explicit owner-only ACL can represent the same effective grants. The schema ACL check now expands `coalesce(nspacl, acldefault('n', nspowner))` through `aclexplode`, sorts the grantee/privilege/grant-option/grantor tuples, and compares the effective privilege inventory across source and restored databases. This is a deterministic regression guard for schema USAGE/CREATE grants, not a substitute for negative role checks. Validate on the exact workflow commit; earlier green runs do not cover this change.
